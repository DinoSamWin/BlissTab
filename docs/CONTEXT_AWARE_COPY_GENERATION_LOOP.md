# StartlyTab 状态感知文案闭环 V1.0

> 状态：当前实现的唯一产品规则说明。旧的 V1/V2/V7 文档仅用于追溯，不再作为运行时 Prompt。
>
> 代码中的唯一 Prompt 源为 `src/services/perspectiveEngine/generator.ts`，本文解释规则、边界和验证方法。

## 1. 产品任务

StartlyTab 是浏览器新标签页里的一句话陪伴。它不是聊天机器人、心理治疗师、效率教练、管理者或监控工具。

这句话只完成三件事：

1. 准确地贴住已经确认的当下，不猜用户没提供的状态。
2. 轻轻打断工作惯性，让用户和眼前的任务松开一点距离。
3. 用自然、轻松、像熟人但不过界的口吻，把注意力还给身体、吃饭、时间、普通物件或屏幕外的生活。

提高效率只能是副作用，不能直接催用户继续工作。

## 2. 不可破坏的原则

优先级固定为：准确性 > 安全感 > 当下匹配 > 新鲜感 > 文采。

- 未知就是未知，不能用默认值伪装成事实。
- 晚上打开浏览器不等于加班；午后回来不等于刚午睡；11:50 不等于用户饿了。
- 没有显式情绪点击时，不能说用户焦虑、疲惫、难过或崩溃。
- 不输出精确时刻、精确标签数、URL、电量、刷新次数或内部传感标签。
- 不使用“加油”“深呼吸”“相信自己”“你已经很棒了”等口号和教练话术。
- 不用问号、感叹号、emoji、Markdown、引号；只输出一句完整短句。
- 中文以 12–28 个可见字符为宜，60 字符硬上限。
- 默认轻松、口语化、带一点小幽默；不堆诗意比喻，不制造“它在监视我”的感觉。

## 3. 输入事实与能力边界

所有环境信号都必须经过用户同意。模型不直接接触浏览器 API，只收到规则引擎生成的 policy packet。

浏览器信号必须带采集时间，超过 2 分钟一律降为未知，防止旧标签负载或旧声音状态污染当前文案。

| 信号 | 网页版 | 扩展版 | 使用边界 |
|---|---|---|---|
| 本地日期、时刻、星期、时区 | 支持 | 支持 | 高置信度，只输出模糊时段，不复述精确时刻 |
| 用户工作/午饭时间 | 契约已支持 | 契约已支持 | 当前 UI 尚未提供设置，缺省为 09:00 / 12:00–13:30 / 18:00 |
| 首次打开、上次打开间隔、当天次数 | 支持，本地保存 | 支持，本地保存 | 只说明回到 StartlyTab，不能推断用户刚休息或刚开完会 |
| 显式情绪点击 | 支持 | 支持 | 唯一可以高置信度描述情绪的来源 |
| 全浏览器标签数量、是否有声音、窗口状态 | 不支持 | 用户同意后支持 | 网页只能数同源 StartlyTab 页面，不能冒充全浏览器标签数 |
| 10 分钟标签切换次数 | 不支持 | 用户同意后支持 | 仅保存时间戳数量，不保存 URL、标题或 tab id |
| 全局键鼠 idle | 不支持 | 当前不支持 | 页面内 inactivity 不能冒充系统 idle，因此当前不上传 |
| 电量 | 浏览器允许且用户同意时 | 同左 | 当前规则不把电量作为文案事实输出 |
| 节假日、调休、第几天 | 输入契约已支持 | 输入契约已支持 | 当前缺权威日历数据源，不允许仅凭周末/日期猜测 |
| 到公司、已下班、正在加班 | 仅显式输入 | 仅显式输入 | 只有 `confirmed_work_status` 或可信工作流输入可确认；时刻和活跃度只能形成弱信号 |

`confirmed_work_status` 支持 `workplace_arrival`、`working`、`off_work`、`overtime`。当前产品没有自动填入它，所以真实运行时不会擅自说“刚到公司”或“正在加班”。

## 4. 时间基底

时间段根据用户工作时间动态计算；以下是默认日程下的结果：

| 时间 | 基础场景 | 回应任务 |
|---|---|---|
| 23:30–05:00 | `night_guard` | 允许未完成，保护夜间边界 |
| 05:00–07:30 | `early_buffer` | 给一天留下缓慢加载空间 |
| 07:30–09:30 | `arrival_buffer` | 不要求人和脑子同时进入状态 |
| 09:30–11:20 | `morning_sustained` | 避免任务一起拥挤 |
| 11:20–12:00 | `pre_lunch_transition` | 让上午和午饭之间出现边界 |
| 12:00–13:30 | `midday_release` | 承认吃饭和空白本身就是生活 |
| 13:30–14:30 | `post_lunch_reentry` | 只说午后重新接入，不说刚睡醒 |
| 14:30–16:45 | `afternoon_stretch` | 轻微感官换挡和范围收缩 |
| 16:45–18:30 | `closing_runway` | 容纳未完成，不制造最后冲刺 |
| 18:30–21:00 | `evening_transition` | 把时间从工作惯性里还给用户 |
| 21:00–23:30 | `late_evening_boundary` | 保护晚间注意力，不自动判定加班 |

边界会随用户配置的上班、午饭和下班时间平移。

## 5. 场景优先级

先保留时间基底，再按以下顺序选择唯一主场景：

1. 用户刚刚显式点击情绪 → `emotional_checkin`。
2. 三次及以上连续手动刷新 → `refresh_loop`。
3. 有可信的“回到 StartlyTab”信号 → `quiet_return`。
4. 扩展确认标签负载较高 → `overloaded_browser`。
5. 以上均未命中 → 使用时间基底。

星期、周末、调休、节前/节中/节后、声音、快速切换等信息作为 modifier 保留，不会覆盖主场景。这样“11:50 + 标签过载”仍知道基础是午饭前，但主任务先帮助用户缩小屏幕范围。

## 6. 节日与特殊日期

- 周一：只承认一周重新开始，不输出“周一焦虑”。
- 周五：允许收尾和释放，但不说用户一定马上下班。
- 周末/公共假期：避免默认工作叙事，使用休息日专用保底库。
- 节前：只有权威日历给出 `days_to_holiday` 后才能提假期临近。
- 假期第几天：由 `holiday_day_index` 提供，不能自行计算猜测。
- 节后第几天：由 `days_since_holiday` 提供；语气以缓慢重新接入为主，不使用“收心”“返工加油”。
- 调休工作日：按照工作日时间轴运行，但允许轻微吐槽日历，不抱怨或煽动抵触。

## 7. 状态指纹与缓存

每次打开先由代码生成状态指纹，包含：本地日期、day kind、星期、基础场景、主场景、modifier、显式情绪、标签负载档位及作用域、回访状态、已确认工作状态、刷新阶段、节日距离/天数、persona、主题集合哈希和语言。

缓存只能在以下条件同时满足时命中：

- 状态指纹完全一致。
- Prompt 版本一致。
- 文案通过当前事实和调性校验。
- 文案没有命中近期文本或语义冷却。

缓存按用户本地日期隔离，避免跨天拿到昨天的“最新状态”。默认一次生成 8 条，池少于 3 条时后台补充。冷启动最多等待模型 1.5 秒；超过预算立即展示与当前状态匹配的本地保底，模型继续在后台填池。已展示的候选不会重新放回池中；同一状态的并发补池会通过内存任务和 45 秒跨标签租约合并，避免重复消耗 token。

这里的“最新”指状态兼容，不是每次都重新调用模型。时段、情绪、假期、工作确认状态或浏览器负载变化会立即换指纹；状态没变时复用已验证候选，减少等待和 token。

## 8. 新鲜感与防重复

去重由代码负责，不寄希望于模型“记得以前说过什么”。历史在本地保留 14 天、最多 100 条。

每条文案必须带以下语义标签：

- `content_track`：内容路线。
- `semantic_core`：稳定含义。
- `action_tag`：隐含的小动作或许可。
- `object_tag`：使用的物件/对象。
- `metaphor_tag`：比喻方式，没有则为 `none`。
- `opener_tag`：开头模式。
- `sentence_shape`：句式结构。

冷却窗口：semantic core 20 条、比喻 10 条、开头 5 条；句式、动作和物件分别参与评分降权。中文表层重复使用字符二元组、三元组和最长公共子序列联合判断，默认相似度阈值为 0.58。

模型只会收到最近 2 条短文本，以及有限数量的近期语义标签，不上传整段历史。这样能同时控制 token 和重复率。

内容路线在以下八类之间做确定性轮换：

- `playful_boundary`：轻松地把用户和工作惯性分开。
- `grounded_observation`：只观察已确认的当下。
- `life_boundary`：给吃饭、休息和屏幕外生活合法空间。
- `sensory_reset`：最多一个安全的小幅视觉/身体换挡，不声称症状。
- `permission_pause`：允许未完成或短暂停留。
- `object_humor`：让普通物件承担一点幽默。
- `philosophical_zoom_out`：只在第五次连续刷新使用；用直白、具体的时间或生活尺度拉远眼前问题，禁止哲学家点名、宇宙星河套话和纯抽象感慨。
- `unexpected_perspective`：用具体的新角度缩小眼前压力，不上价值。

同一天、同一场景、同一历史下，路线选择是可复现的；近期用过的路线会被绕开。无限期绝不重复在有限文案空间里无法数学保证，因此规则保证冷却窗口内强去重，池耗尽后选择最久未出现的本地保底。

## 9. 模型 Prompt 契约

模型保持现有 DeepSeek/SiliconFlow 配置。模型只负责“渲染文案”，无权重新判断状态。

System Prompt 的核心身份：

```text
You are StartlyTab, a one-line companion that appears on the user's browser new-tab page.
You are NOT a chatbot, therapist, productivity coach, motivational quote generator, manager, or surveillance system.
Accurately acknowledge the resolved moment, loosen the user's grip on work for a second, and remind them that life outside the screen still exists.
Upstream deterministic rules already resolved scene, intent, confidence, allowed facts, and novelty direction. Do not reinterpret state or invent missing context.
Return only a valid JSON array.
```

User Prompt 是一个可审计 policy packet，包含：

- 已确定的 scene、base scene、modifier、intent、strategy、confidence 和 persona。
- `known_facts` 与逐条 `forbidden_assumptions`。
- 本轮目标路线、允许路线、所有需要避开的近期语义标签。
- 连续刷新阶段的专用指令。
- 用户主题，但最多影响 25% 措辞，不能覆盖事实边界。
- JSON 输出字段和长度约束。

状态指纹和 Prompt 版本由应用在解析后绑定，模型不重复输出，避免批量生成时浪费 token。

## 10. 本地候选校验

每个模型候选必须经过代码校验，失败即淘汰：

- 空文本、多行、问号/感叹号、精确时刻、过长、口号或教练腔。
- 编造标签负载、声音、天气、假期、情绪、午睡、饥饿、会议、到公司、下班或加班。
- 状态指纹或 Prompt 版本与缓存不一致。
- 缺少语义去重字段，或内容路线不在当前允许集合。
- 与历史表层文本、semantic core、比喻或开头重复。

全部候选被拒、无 Key、断网或超时时，使用状态感知的本地中文保底；不会退回与时段无关的随机句子。

## 11. 反馈闭环

一次展示后的反馈按以下方式进入下一轮：

```text
展示文案
  → 本地记录文本 + 场景 + 路线 + 七类语义标签
  → 下一次状态解析
  → 状态兼容缓存过滤
  → 路线轮换与多层冷却
  → 模型候选校验 / 本地保底
  → 新展示
```

手动刷新本身就是负反馈，并由代码固定路线：第一次感官换焦，第二次普通物件，第三次轻松打断，第四次转向屏幕外生活，第五次进入有现实锚点的哲学拉远，第六次及以后明确允许离开或关闭页面。第五次必须落到页面、任务、今天、明天或几分钟等具体对象；只讲宇宙、意义、无常等抽象概念的候选会被代码淘汰。停顿三分钟后刷新计数归零。

当前已有停留时长/内容 track 反馈数据，但尚未接入新路线选择，不能声称系统已经学会个人偏好。接入前应先定义最低样本量、衰减和探索比例，避免一次误触永久改变风格。

## 12. 发布前门槛

必须同时满足：

1. 固定场景测试通过，包括周一 20:10、周二 07:00、周二 11:50、午前标签过载、网页版未知信号、显式焦虑、连续刷新、节前/假期和中文近似重复。
2. 候选事实边界测试通过，尤其不能靠时间推断到公司、午睡、下班或加班。
3. 缓存命中、过期、池耗尽、无网和全部候选拒绝路径均有状态化保底。
4. 线上记录匿名聚合指标：缓存命中率、首屏耗时、模型调用率、候选拒绝原因、保底率、连续刷新率和 14 天重复率；不记录 URL、标题或浏览历史。
5. 模型密钥只能位于服务端，客户端使用受鉴权和限流的生成接口。

## 13. 当前模型结论

现有 DeepSeek Chat / DeepSeek V3 足以承担受约束的短中文改写，当前阶段不需要为了“更智能”立即换更大模型。效果上限更依赖输入可信度、规则包、候选校验和评测数据，而不是模型推理深度。

继续使用当前模型的前提：

- 保持“规则判断在代码、模型只写句子”的职责边界。
- 使用批量生成和本地池，限制输出 token；当前 temperature 为 0.9，适合新鲜感，后续用离线样本比较 0.7/0.8/0.9。
- 若服务商支持稳定的 JSON Schema/structured output，应替换当前流式对象提取。
- 用真实场景集评估事实错误率、重复率、调性通过率和用户刷新率，而不是凭几条好文案判断模型。

模型目前无法弥补的不是文案能力，而是三个数据缺口：权威节假日日历、用户可配置作息、显式工作状态来源。补齐这些输入比换模型更能提升“它真的懂现在”的感觉。
